## 1. 문제 정의

### 1.1 Cold Start 구간이란

사용자가 가입 후 첫 번째 핵심 행동(책 추가, 노트 작성)을 완료하기까지의 구간.
이 구간에서 사용자는 **빈 대시보드**를 마주하며 "무엇을 해야 하지?"라는 결정 마비(Decision Paralysis)를 경험한다.

### 1.2 현재 사용자 경험 흐름

```
가입 완료
  → 대시보드 진입
    → NoReadingBookCard 표시 ("첫 책을 추가해보세요")
      → "책 추가하기" CTA 클릭
        → /books/search 이동
          → 빈 검색 화면 (무엇을 검색?)
            → 검색어 입력
              → 결과에서 책 선택
                → 책 추가 완료
```

**문제**: 가입에서 첫 책 추가까지 **6단계**가 필요하고, 중간에 "무엇을 검색할지" 결정해야 하는 마찰 지점이 존재.

### 1.3 핵심 이탈 포인트

| 이탈 포인트 | 원인 | 영향도 |
|------------|------|--------|
| 빈 대시보드 | 가치를 느끼기 전에 빈 화면 노출 | 높음 |
| 검색 초기 화면 | 무엇을 검색할지 모름 | 높음 |
| 온보딩 5개 항목 | 인지부하로 행동 지연 | 중간 |
| 빈 상태 메시지 | 중립적 톤으로 동기부여 부족 | 중간 |
| Tertiary Zone 미표시 | 서비스 가치를 미리 보여주지 못함 | 낮음 |

## 2. 전략 1 - 위시리스트: "읽고 싶은 책" 상태 활용

### 2.1 핵심 아이디어

기존 `reading_status` enum의 `not_started`를 **"읽고 싶은 책"(위시리스트)**으로 리포지셔닝.
책을 실제로 읽기 시작하지 않아도, "읽고 싶다"는 의사 표현만으로 첫 행동을 완료하게 만든다.

### 2.2 현재 구현 상태

```typescript
// types/database.ts - reading_status enum
reading_status: "not_started" | "reading" | "completed" | "paused" | "rereading"
```

- `not_started` 상태가 이미 존재하지만, UI에서 "읽고 싶은 책"이라는 맥락으로 활용되지 않음
- `book-status-badge.tsx`, `book-status-selector.tsx`, `status-filter.tsx`에서 `not_started` 처리 중

### 2.3 개선 방향

| 항목 | 현재 | 개선 후 |
|------|------|---------|
| 상태 라벨 | "읽기 전" (중립적) | "읽고 싶어요" (적극적, 감정적) |
| 등록 플로우 | 검색 → 책 상세 → 상태 선택 | 검색 → "읽고 싶어요" 원탭 등록 |
| 대시보드 노출 | 미표시 | "읽고 싶은 책" 섹션 추가 |
| Cold Start 효과 | 없음 | 위시리스트 등록 = 첫 행동 달성 |

### 2.4 구현 포인트

- **NoReadingBookCard 이중 CTA**: "책 추가하기"와 "읽고 싶은 책 찾기" 두 가지 행동 제공
- **검색 결과에 "읽고 싶어요" 버튼**: 책 상세 페이지 거치지 않고 검색 결과에서 바로 위시리스트 등록
- **대시보드 위시리스트 섹션**: 읽는 책이 없어도 "읽고 싶은 책" 목록 표시
- **위시리스트 → 읽기 시작 전환 유도**: "이 책을 읽기 시작하셨나요?" 넛지

### 2.5 기대 효과

- **첫 행동까지의 마찰 감소**: 6단계 → 3단계 (검색 → 원탭 등록 → 완료)
- **빈 대시보드 해소**: 위시리스트라도 있으면 대시보드가 풍성해짐
- **자연스러운 전환**: 위시리스트 → 읽기 시작 → 기록 작성의 점진적 여정

## 3. 전략 2 - 책 발견: 인기 도서 섹션 및 검색 초기 화면 개선

### 3.1 핵심 아이디어

검색 페이지 진입 시 빈 화면 대신, 탐색할 수 있는 콘텐츠를 제공하여 "무엇을 검색할지 모르겠다"를 해소.

### 3.2 인기 도서 섹션

**데이터 소스 옵션:**

| 소스 | 장점 | 단점 |
|------|------|------|
| ReadTree 내부 데이터 | 커뮤니티 맥락, 실시간 | RLS 정책 필요, 초기 데이터 부족 |
| 네이버 검색 API 인기 키워드 | 트렌드 반영 | API 레이트리밋, 비용 |
| 수동 큐레이션 | 품질 높음 | 운영 비용 |

**권장 접근**: 초기에는 ReadTree 내부 데이터(가장 많이 추가된 책) + 수동 큐레이션 병행, 규모 확장 시 자동화.

### 3.3 검색 초기 화면 구성

```
[검색 입력 필드]

--- 인기 도서 ---
[책 카드] [책 카드] [책 카드] [책 카드]
  + "읽고 싶어요" 원탭 버튼

--- 카테고리 ---
[소설] [에세이] [자기계발] [인문] [과학] [경제]

--- 최근 추가된 책 (커뮤니티) ---
"N명이 읽고 있어요"
[책 카드] [책 카드] [책 카드]
```

### 3.4 구현 시 주의사항

- **RLS 정책**: 인기 도서 집계 시 `user_books` 테이블의 개인정보 보호 (집계 데이터만 노출, 개별 사용자 정보 비노출)
- **네이버 API 레이트리밋**: 검색 요청 캐싱 필요 (Vercel Edge Config 또는 Supabase cache)
- **빈 데이터 대비**: 초기에 인기 도서 데이터가 부족할 때의 폴백 콘텐츠

## 4. 전략 3 - Quick Note: 온보딩 단순화 및 Empty State 격려 톤

### 4.1 온보딩 체크리스트 단순화

**현재 (5개 항목):**

| 항목 | 보상 | 핵심 여부 |
|------|------|----------|
| 첫 책 추가 | 35p | 핵심 |
| 첫 노트 작성 | 25p | 핵심 |
| 나무 물주기 | 10p | 부가 |
| 목표 설정 | 20p | 부가 |
| 페르소나 탐험 | 15p | 부가 |

**개선 (Phase 1: 핵심 3개 → Phase 2: 나머지 잠금 해제):**

Phase 1 (즉시 표시):
1. 첫 책 추가 (35p) - "읽고 싶은 책을 찾아보세요"
2. 첫 노트 작성 (25p) - "인상 깊은 문장을 기록해보세요"
3. 목표 설정 (20p) - "올해 몇 권 읽을까요?"

Phase 2 (Phase 1 완료 후 잠금 해제):
4. 나무 물주기 (10p)
5. 페르소나 탐험 (15p)

기존 `EmptyState` 컴포넌트의 `variant`, `nextStepHint` 속성을 활용하여 각 페이지별 빈 상태 메시지를 개선.

## 5. 전략 4 - 소셜 프루프: "N명이 읽는 중" 표시

### 5.1 핵심 아이디어

다른 사용자들의 독서 활동을 집계하여 "이 책을 12명이 읽고 있어요" 같은 소셜 프루프를 제공.
결정 마비를 줄이고, "다른 사람들도 읽는 책이니 나도 읽어볼까"라는 동기부여.

### 5.2 구현 접근

```sql
-- 인기 도서 집계 뷰 (RLS 고려)
CREATE VIEW popular_books_summary AS
SELECT
  b.id, b.title, b.author, b.cover_image_url,
  COUNT(ub.id) AS reader_count,
  COUNT(CASE WHEN ub.status = 'reading' THEN 1 END) AS active_reader_count
FROM books b
JOIN user_books ub ON ub.book_id = b.id
GROUP BY b.id
HAVING COUNT(ub.id) >= 3  -- 최소 3명 이상
ORDER BY reader_count DESC;
```

### 5.3 표시 위치

- 검색 결과의 각 책 카드에 "N명이 읽는 중"
- 인기 도서 섹션
- 책 상세 페이지

### 5.4 프라이버시 고려

- 개별 사용자가 어떤 책을 읽는지는 비공개 유지
- 집계 숫자만 표시 (최소 3명 이상일 때만)
- 사용자가 자신의 독서 목록 공개 여부 선택 가능

## 7. 추적 지표 설계

### 7.1 전환 퍼널

```
방문 (Landing Page View)
  → 가입 (Sign Up Complete)
    → 첫 책 추가 (First Book Added)
      → 첫 노트 작성 (First Note Created)
        → 7일 리텐션 (D7 Return)
          → 30일 리텐션 (D30 Return)
```

| 구간 | 지표 | 현재 추정 | 목표 |
|------|------|----------|------|
| 방문 → 가입 | 가입 전환율 | 측정 필요 | 15% |
| 가입 → 첫 책 | 첫 책 전환율 | ~40% | 70% |
| 첫 책 → 첫 노트 | 첫 노트 전환율 | ~30% | 50% |
| 첫 노트 → D7 | 7일 리텐션 | 측정 필요 | 30% |
| D7 → D30 | 30일 리텐션 | 측정 필요 | 15% |

### 7.2 행동 지표

| 지표 | 정의 | 측정 방법 | 목표 |
|------|------|----------|------|
| 가입 후 24시간 내 첫 책 비율 | 가입 → 24시간 내 첫 책 추가 | `user_books.created_at - users.created_at` | 60% |
| 검색 → 추가 전환율 | 검색 수행 → 책 추가 완료 | 이벤트 트래킹 | 40% |
| 위시리스트 → 읽기 시작 전환율 | `not_started` → `reading` 상태 변경 | `user_books.status` 변경 추적 | 30% |
| 온보딩 완료율 | 체크리스트 전체 완료 | `onboarding` 테이블 | 60% |
| 빈 상태 CTA 클릭율 | EmptyState 버튼 클릭 | 이벤트 트래킹 | 20% |

### 7.3 건강 지표

| 지표 | 정의 | 측정 주기 | 목표 |
|------|------|----------|------|
| DAU/WAU | 일간/주간 활성 사용자 비율 | 일별 | 0.3 이상 |
| 주간 기록 수 | 사용자당 주간 노트 수 | 주별 | 3개 이상 |
| 스트릭 평균 | 전체 사용자 평균 연속 기록일 | 주별 | 3일 이상 |
| 월간 책 추가 수 | 사용자당 월간 신규 책 | 월별 | 2권 이상 |
| NPS | 순추천지수 | 분기별 | 50 이상 |

## 8. 위험 요소 및 완화 전략

### 8.1 인기 도서 RLS 정책

**위험**: 인기 도서 집계 시 `user_books` 테이블의 개인정보가 노출될 수 있음.

**완화**:
- 집계 뷰를 별도 생성하여 개인 정보 제거
- `security_definer` 함수로 집계 처리
- 최소 N명 이상인 경우만 표시 (K-Anonymity 원칙)

### 8.2 네이버 API 레이트리밋

**위험**: 인기 도서, 카테고리별 추천 등 추가 API 호출로 레이트리밋 도달 가능.

**완화**:
- 인기 도서 목록을 캐싱 (1시간~24시간 주기 갱신)
- 카테고리별 추천은 초기에 수동 큐레이션으로 대체
- API 호출 모니터링 및 알림 설정

### 8.3 기존 UX와 일관성

**위험**: 빈 상태 메시지 톤 변경이 기존 사용자에게 혼란을 줄 수 있음.

**완화**:
- EmptyState 컴포넌트의 기존 API(`variant`, `nextStepHint`)를 활용하여 일관된 패턴 유지
- 디자인 가이드라인(`doc/design/DESIGN_GUIDELINES.md`)과 정합성 확인
- 점진적 롤아웃 (Phase별 적용)

### 8.4 데이터 부족 시 소셜 프루프 역효과

**위험**: 초기에 사용자 수가 적으면 "2명이 읽는 중"이 오히려 부정적 인상.

**완화**:
- 최소 표시 기준 설정 (예: 5명 이상)
- 초기에는 소셜 프루프 비활성화, 사용자 기반 성장 후 활성화
- 대안으로 "이번 주 인기 도서" 같은 트렌드 표현 활용

### 8.5 온보딩 단순화의 부작용

**위험**: 체크리스트 항목 축소로 기존 보상 체계(포인트)와 불일치.

**완화**:
- 총 보상 포인트는 유지하되, Phase 1/2로 분할
- Phase 2 잠금 해제 시 추가 보너스 포인트 제공
- 기존 사용자의 진행 상태 마이그레이션 고려
