# Cloud Run 유휴 과금 — min-instance 상시 기동

> **발견**: 2026-07-24 · **조치 완료**: 2026-07-24 (동일자)
> **영향액**: 연 약 ₩83,000 (실 발생 ₩37,969 / 1~7월)
> **심각도**: P1 — 금액은 작으나 6개월간 무감지, 재발 시 규모 확대 가능

---

## 한 줄 요약

관리자 OCR용 Cloud Run 서비스가 **요청 0건인 상태로 3개월간 24시간 켜져 있었고**, 그 유휴 비용이 전체 청구액의 99.99%였다.

## 원인 규명

### 1단계 — SKU로 그룹화하니 정체가 드러남

| SKU | 사용량 | 소계 |
|---|---|---|
| Services **Min Instance** Memory | 963,610 GiB-초 | ₩2,316 |
| Services **Min Instance** CPU | 1,927,221 vCPU-초 | ₩766 |
| Services CPU (실제 요청 처리) | **38.75초** | ₩0 |
| Requests | **6건** | ₩0 |

22일간 요청 6건인데 CPU는 192만 초가 청구됐다.

### 2단계 — 산술 검증

```
1,927,221 vCPU-초 ÷ 22일 = 87,601초/일
1 vCPU × 24시간          = 86,400초/일
→ 오차 1.4%, 정확히 인스턴스 1개가 상시 기동
```

메모리도 동일: `963,610 GiB-초 ÷ 22일 ÷ 0.5GiB ≈ 87,600초/일`.

### 3단계 — 콘솔 설정 확인

```
확장: 자동(최소: 1개, 최대: 10개)   ← 범인
```

### 4단계 — 낭비 확증 (DB 교차 검증)

```sql
select to_char(created_at,'YYYY-MM') ym, count(*) from ocr_logs group by 1 order by 1 desc;
```

| 월 | 건수 |
|---|---|
| 2026-04 | 2 |
| 2026-05 | **0** |
| 2026-06 | **0** |
| 2026-07 | **0** |

Cloud Run 누적 요청 342건 ≈ `ocr_logs` 331행으로 교차 검증됨(차이는 헬스체크·실패 요청).
**결론: 3개월째 아무도 쓰지 않는 기능에 매달 ₩7,000을 지불 중이었다.**

## ⚠️ 핵심 함정 — 리비전 설정과 서비스 설정은 별개다

가장 시간을 많이 잡아먹은 지점. Cloud Run의 min-instance는 **두 군데**에 있다.

| 구분 | 위치 | 이 사건에서의 값 |
|---|---|---|
| **리비전 수준** | 서비스 상세 → `새 버전 수정 및 배포` → "버전 확장" | **0** (문제 없음) |
| **서비스 수준** | 서비스 상세 헤더 우측 **연필 아이콘** (툴팁: "서비스 수준 확장 설정 수정") | **1** ← 진짜 범인 |

배포 페이지만 보면 "최소 인스턴스 0인데 왜 과금되지?"에서 막힌다. **새 리비전을 배포해도 서비스 수준 설정은 바뀌지 않는다.**

조치 경로:
```
console.cloud.google.com/run/detail/us-central1/<서비스명>/metrics?project=<프로젝트ID>
→ 헤더 우측 "확장: 자동(최소: N개, 최대: M개)" 옆 연필 아이콘
→ 인스턴스 최소 개수 = 0 → 저장
```

CLI로는:
```bash
gcloud run services update extracttextfromimage \
  --region us-central1 --project gen-lang-client-0287655743 \
  --min-instances 0
```

## 조치

**서비스 수준 min-instance 1 → 0** (2026-07-24 적용, 콘솔 토스트 "서비스 확장 설정이 업데이트됨" 확인)

```
변경 전: 확장: 자동(최소: 1개, 최대: 10개)
변경 후: 확장: 자동(최소: 0개, 최대: 10개)
```

**트레이드오프**: 첫 호출 시 콜드스타트 수 초 발생. 관리자 전용 OCR이므로 허용 가능하다고 판단(`시작 CPU 부스트`가 켜져 있어 완화됨).

**대안으로 검토했으나 택하지 않은 것**: 서비스 완전 삭제. 비용은 확실히 0이 되지만 `lib/api/cloud-run-ocr.ts` 호출부가 깨지고 재사용 시 재배포가 필요해, 코드 수정 없이 비용만 제거하는 min-instance 0을 택했다.

## 배운 것

1. **요청 기반 과금이어도 min-instance는 예외다.** "요청 없으면 0원"이라는 인식이 이 사고를 6개월간 가렸다. min-instance는 idle 상태에도 CPU·메모리를 청구한다.
2. **청구서만으로는 낭비를 못 찾는다.** 서비스 단위 금액은 "쓰니까 나오는 돈"처럼 보인다. **DB 사용량과 대조**해야 "안 쓰는데 나오는 돈"이 드러난다.
3. **AI Studio·Firebase가 자동 생성한 프로젝트를 놓치기 쉽다.** 프로젝트 ID가 `gen-lang-client-0287655743`처럼 알아보기 힘든 이름이라 존재 자체를 잊는다.
4. **기능을 안 쓰게 됐을 때 인프라를 내리는 절차가 없었다.** 사용량이 308 → 2로 줄어든 2~4월에 알아챌 기회가 있었다.
