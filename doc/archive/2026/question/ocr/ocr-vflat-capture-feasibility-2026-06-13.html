1 배경 — 왜 검토하는가

요청: vFlat의 기능·품질을 분석하고, ReadTree 적용 방법·검토사항·비용·적용 가능 범위를 문서화 + HTML 보고서화

검토를 통해 드러난 핵심 전제 3가지:

  • ReadTree는 이미 OCR을 한다. 캡처 사진 → Supabase Storage → Google Cloud Run OCR → 선택적 AI 텍스트 보정(GPT/Gemini/Claude) → transcriptions 저장. 통계·쿼터·레이트리밋·캐시·배치 보정까지 운영 중.
  • 격차는 "전처리"다. 현재 캡처는 <input type="file" capture="environment">로 정지 사진 1장을 받아 압축만 한다. 곡면 보정·손가락 제거·테두리 인식·자동 촬영이 전혀 없다.
  • vFlat의 본질은 캡처 전처리다. "전문 북스캐너처럼" 보이는 이유는 OCR 엔진이 아니라 촬영 순간의 AI 보정이다.
본 검토의 질문 한 문장: "네이티브 앱 vFlat의 캡처 전처리 품질을, 웹앱인 ReadTree에서 어디까지·어떻게·얼마의 비용으로 따라잡을 수 있는가?"

3 vFlat(VPLAT) 분석

정체·기술·핵심 기능 6가지와 ReadTree 적용 시 필요한 기술 매핑

정체 및 포지션

  • 제품: vFlat Scan — PDF Scanner, OCR (개발사 VoyagerX, 패키지 com.voyagerx.scanner)
  • 형태: 네이티브 iOS/Android 앱. 무료 + 인앱결제(OCR 100p 한도 후 크레딧/광고)
  • 공개 API/SDK: 없음 소비자 앱 전용 → ReadTree "직접 연동" 불가, "방식 차용"만 가능
  • 기술: 온디바이스 딥러닝 — TensorFlow Lite GPU delegate로 책 검출·보정을 단말에서 실시간 추론

핵심 기능 6가지 (= 따라잡아야 할 품질 항목)

#vFlat 기능효과적용 시 필요한 기술웹 난이도
1테두리 자동 인식·크롭어느 각도에서도 페이지만 추출윤곽 검출+코너(OpenCV.js)중
2원근/기울기 보정비스듬해도 정면처럼warpPerspective중
3곡면 보정(dewarp)휜 면을 펼침딥러닝 dewarp 모델상(웹 비현실)
4손가락 자동 제거누른 손가락 지움세그멘테이션+인페인팅상(웹 비현실)
5자동 촬영안정 시 자동 셔터 → 대량 빠름실시간 프레임+코너 안정화중
6양면 동시·분할펼친 책 한 번에 2p중앙 분할+페이지별 보정중~상
—OCR / TTS / 내보내기텍스트화·낭독·내보내기OCR은 ReadTree 이미 보유보유
통찰: 1·2·5(테두리·원근·자동촬영)는 브라우저 오픈소스로 상당 부분 재현 가능. 3·4(곡면·손가락 제거)는 딥러닝이 필요해 웹 단독으로는 비현실적 — 이 둘이 "웹앱이 네이티브를 100% 못 따라가는 경계선"이다.

4 결정적 제약 — 웹앱 아키텍처

ReadTree는 Next.js PWA 웹앱. 브라우저 카메라의 한계가 적용 범위를 티어로 가른다

방식설명전처리 가능성
<input capture> 현행네이티브 카메라 호출 → 정지 사진 1장촬영 후 후처리만(라이브 가이드 불가)
getUserMedia()라이브 카메라 스트림을 <video>/<canvas>로실시간 분석·자동촬영·테두리 가이드 가능

핵심 제약

  • HTTPS 필수 — getUserMedia는 보안 컨텍스트에서만. (Vercel HTTPS → 충족)
  • iOS Safari 제약 — 카메라 권한·자동재생·백그라운드 처리 제약 → UX 예외처리 필요
  • 온디바이스 GPU ML 실시간 처리는 비현실적 — dewarp/손가락 제거 같은 무거운 딥러닝을 브라우저 실시간으로 돌리는 것은 성능·번들상 사실상 불가(저사양 모바일 발열·지연)
  • 번들 비용 — OpenCV.js WASM ~8MB → 페이지 로드 차단 위험 → 지연 로드(동적 import) 필수
결론: "vFlat을 그대로 웹에 이식"은 불가능. 현실적 목표는 테두리·원근·자동촬영을 웹으로 재현해 OCR 입력 품질을 크게 올리는 것이며, 곡면·손가락 제거가 필요하면 클라우드(Tier2)/상용 SDK(Tier3)로 보완한다.

6 권장 전략 — 단계적 균형 로드맵

Tier1을 저비용으로 즉시 도입, Tier2/3는 데이터로 효과를 검증한 뒤 게이트를 통과할 때만 확대

Phase A
Tier 1
브라우저 스캔 모드 — 테두리·원근·자동촬영 + 한 기록당 최대 3페이지. 비용 ≈ 개발 공수.
진입: 즉시 착수 · 게이트: OCR 인식 만족도/재촬영율 측정
Phase B
Tier 2
클라우드 전처리 — 곡면/손가락이 인식률 저해의 핵심으로 확인되면 dewarp/finger-removal 추가.
진입: A 측정에서 곡면/손가락 실패가 유의미할 때 · 게이트: 페이지당 추가비용 대비 개선폭
Phase C
Tier 3
상용 웹 SDK — 캡처 품질이 핵심 KPI로 격상되면 무료 트라이얼로 벤치마크.
진입: B로도 부족 + 품질이 전환·리텐션에 직결 · 게이트: 연 라이선스 ROI 판단
Tier 4(네이티브)는 본 로드맵과 분리한 별도 플랫폼 전략 의제로 둔다(앱 출시·스토어 운영은 기능 1건의 범위를 초과).

7 상세 적용 방법 — Phase A 구현 설계 (Tier 1)

UX 흐름 · 신규/재사용 컴포넌트 · 기술 포인트 · 다중 페이지(≤3) 데이터 모델

7.1 UX 흐름

  • 기록 작성(RecordSheet 필사 단계)/노트 작성에 "스캔" 진입점 추가(기존 카메라/앨범 옆)
  • "스캔" → 라이브 카메라(getUserMedia) 풀스크린 + 검출 테두리 가이드 오버레이
  • 안정 검출 시 자동 촬영(또는 수동 셔터) → 즉시 원근 크롭 + 대비 향상 미리보기
  • 페이지 큐(최대 3페이지)에 추가 — 페이지별 미리보기·재촬영·삭제
  • "완료" → 압축 → 업로드 → OCR → 추출 텍스트를 필사/발췌 편집기로 전달

7.3 기술 포인트

  • 검출 라이브러리: jscanify(OpenCV.js 기반) 또는 OpenCV.js 직접. 동적 import + 지연 로드로 ~8MB WASM이 초기 로딩을 막지 않게 — 스캔 진입 시에만 로드
  • 자동 촬영 판정: 최근 N프레임 코너가 임계값 내 안정 → 셔터. 코너 undefined(부분 가림)면 대기
  • 대비 향상: 그레이스케일 + 적응형 임계처리로 OCR 친화 이미지 생성(선택)
  • 폴백: getUserMedia 미지원/권한 거부/저사양 → 기존 file-input 모드로 자동 전환(기능 손실 없음)

7.4 다중 페이지(최대 3) 데이터 모델 — 결정 필요

옵션구조장점단점
(a) 페이지당 노트3p → 노트 3개(각 1:1)스키마 무변경, 단순"1 기록=1 항목"과 어긋남, 분산
(b) 1노트+3이미지노트 1 + 이미지 3 + transcriptions 1:N(page_index)한 항목에 묶임(요청 부합)마이그레이션(UNIQUE 해제) + RLS 재점검
(c) 1노트+텍스트 결합3p OCR 결과 합쳐 단일 quote_content스키마 최소 변경페이지 경계·재OCR 추적 약함
권장: 1차는 (c) 또는 (a)로 스키마 충격 없이 출시 → 사용 패턴 확인 후 필요 시 (b)로 정식 확장. (b) 채택 시 doc/database/에 Idempotent 마이그레이션 + RLS 4종 필수. reading_logs.image_urls(≤5 JSONB)는 스탬프 경로와 이미 정합.
