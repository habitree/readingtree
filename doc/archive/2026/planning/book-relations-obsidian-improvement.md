# 책 연결관계 개선 기획 — Obsidian 스타일 지식 그래프

> 작성일: 2026-06-15 · 상태: 검토용 초안(Draft) · 대상: Habitree Reading Hub v4.x
> 목적: 사용자가 자신의 책들 간 연결을 **한눈에 보고, 쉽게 만들고, 자연스럽게 탐색**하도록 개선

---

## 1. 배경 및 목적

현재 책 연결관계는 "책 상세 페이지에서 관련 도서를 썸네일로 나열"하는 수준에 머물러 있다. 연결을 만들 수는 있지만, **전체 연결망을 조망**하거나 **연결을 따라 탐색**하거나 **왜 연결했는지 맥락을 남기는** 경험은 없다.

Obsidian이 주는 핵심 가치는 다음과 같다:

- **전역 그래프(Global Graph)**: 내 지식 전체가 노드-엣지로 한 화면에 보인다.
- **로컬 그래프(Local Graph)**: 지금 보는 문서를 중심으로 이웃 연결만 본다.
- **백링크/아웃링크 패널**: "이 문서를 가리키는 것 / 이 문서가 가리키는 것"을 항상 곁에서 본다.
- **마찰 없는 연결 생성**: `[[ ]]` 한 번으로 연결이 생기고, 끊긴 연결도 시각적으로 드러난다.

이 기획은 위 4가지를 **독서 도메인에 맞게 번역**하여 사용자 기능으로 끌어올리는 것을 목표로 한다.

## 2. 현행 분석 (As-Is)

### 2.1 데이터 모델

**`user_book_relations`** (양방향 명시적 연결)

| 컬럼 | 설명 |
|------|------|
| `id` | PK |
| `user_id` | 소유자 (RLS: `auth.uid() = user_id`) |
| `source_user_book_id` | 출발 책 (`user_books.id`) |
| `target_user_book_id` | 도착 책 |
| `reason` | 연결 사유 (TEXT, **현재 admin 전용**, NULL 허용) |
| `created_at` | 생성 시각 |

- **양방향 저장 방식**: A↔B 연결 시 `A→B`, `B→A` 두 행을 모두 insert. 조회/삭제가 단순해지는 대신 행이 2배.
- 제약: 자기 연결 금지(`different_books`), 중복 금지(`UNIQUE(user_id, source, target)`).
- 인덱스: `user_id`, `source`, `target` 각각 존재.

**`notes.related_user_book_ids`** (UUID[], GIN 인덱스) — 기록(노트)이 참조하는 다른 책들. `syncBookRelationsFromNote()`가 이 배열로부터 `user_book_relations`를 **자동 생성**(관련 책들끼리 전부 양방향 연결)한다. 즉 **연결의 출처가 두 갈래**다: ① 사용자가 직접 만든 연결, ② 노트 작성 시 자동 파생된 연결. 현재 둘은 저장 후 구분되지 않는다.

### 2.2 사용자 대면 UI (한계)

| 컴포넌트 | 역할 | 한계 |
|----------|------|------|
| `RelatedBooksList` | 책 상세에서 연결된 책 표지 그리드 | 평면 나열, 1촌만 보임, 맥락 없음 |
| `RelatedBooksEditor` | 다이얼로그에서 라이브러리 검색 → 1건씩 추가/삭제 | 한 번에 하나, 사유 입력 불가, 양방향 추천 없음 |
| `book-linked-free-notes` | 책에 연결된 자유기록 표시 | 책↔노트만, 책↔책 그래프와 분리 |

→ **전역 조망 없음 / 탐색 흐름 없음 / 연결 이유 없음 / 끊긴 지식 발견 불가.**

### 2.3 이미 보유한 자산 — admin 그래프 (재사용 핵심)

`components/admin/book-relations-graph.tsx` (771줄)에 **완성도 높은 force-directed SVG 그래프**가 이미 있다:

- 골든앵글 초기 배치 + 반발/인력/센터링 물리 시뮬레이션 (외부 라이브러리 없이 순수 구현)
- 줌/팬/노드 드래그, 연결 수 배지, 책 표지를 노드 카드로 렌더, 선택/호버 시 이웃 하이라이트·나머지 디밍, 엣지 흐름 애니메이션
- 짝꿍 컴포넌트: `book-relations-inspector`(상세 패널), `-table`, `-stats-detail`, `-dashboard`

**이 엔진은 admin 데이터(전 사용자)를 그리도록 묶여 있을 뿐, 알고리즘 자체는 사용자 1인 데이터에 그대로 쓸 수 있다.** → 개선의 상당 부분이 "신규 개발"이 아니라 **"기존 그래프 엔진을 공용 컴포넌트로 추출 + 사용자 데이터 연결"**이다. 이것이 이 기획의 비용을 크게 낮춘다.

## 3. 문제 정의 (Obsidian 대비 갭)

| Obsidian 개념 | 현재 ReadingTree | 갭 |
|---------------|------------------|-----|
| 전역 그래프 | 없음(사용자) | **신규 화면 필요** (admin 엔진 재사용) |
| 로컬 그래프 | 평면 썸네일 리스트 | **책 중심 미니 그래프로 교체** |
| 백링크/아웃링크 패널 | 1촌 리스트만 | **연결 맥락 패널 통합**(책↔책 + 책↔노트) |
| `[[ ]]` 즉시 연결 | 다이얼로그 1건씩 | **빠른 연결·다중 선택·사유 입력** |
| 끊긴 노드/고립 노드 시각화 | 없음 | **고립 책 발견 기능** |
| 태그/색상 그룹핑 | 없음 | **연결 유형·서가별 색상** |

## 4. To-Be: 핵심 컨셉

> **"내 서재를 하나의 생각 지도로." — 책은 점, 함께 읽은 맥락은 선.**

사용자가 (1) 전체 지도에서 자신의 독서 세계를 조망하고, (2) 특정 책에서 이웃으로 자연스럽게 건너뛰며, (3) 왜 연결했는지 한 줄을 남겨 의미를 축적하고, (4) 아직 연결되지 않았지만 연관 있는 책을 제안받는 경험.

## 5. 기능 제안 (상세)

### F1. 전역 연결 지도 (Global Graph) — *최우선*

- 신규 라우트 `app/(main)/library/graph` (또는 서재 탭 내 "지도" 뷰 토글).
- admin 그래프 엔진을 추출한 공용 `<KnowledgeGraph>`에 **현재 사용자의 `user_book_relations` + 책 메타**를 주입.
- 인터랙션: 노드 클릭 → 우측 인스펙터(표지·제목·저자·연결 수·연결된 책/노트 목록·"책으로 이동"). 검색/필터(서가, 연결 수, 고립 노드만), 색상 그룹핑(서가 또는 연결 유형).
- 빈/소량 상태: 연결 0~1개 사용자에게는 그래프 대신 "첫 연결 만들기" 온보딩.
- 성능: 노드 수 많을 때 라벨 simplification, 시뮬레이션 tick 상한(이미 `maxTicks` 존재), 200+ 노드 시 정적 레이아웃 캐싱 고려.

### F2. 로컬 그래프 (책 상세) — *최우선*

- `RelatedBooksList`(평면 그리드)를 **현재 책 중심 1~2촌 미니 그래프**로 교체 또는 토글 제공.
- 중심 노드 = 현재 책, 1촌 = 직접 연결, (옵션) 2촌 = 이웃의 이웃을 흐리게 → **간접 연관 발견**.
- 노드 클릭으로 해당 책 상세로 이동, 엣지 hover 시 사유(reason) 툴팁.

### F3. 연결 맥락 패널 (Backlinks 통합)

- 책 상세에 **"이 책과 이어진 것"** 단일 패널: 책↔책 연결 + 이 책을 `related_user_book_ids`로 참조하는 노트 + 이 책에 달린 자유기록을 한곳에 모음.
- 각 항목에 출처 배지: `직접 연결` / `기록에서 파생` / `노트 참조`.

### F4. 마찰 없는 연결 생성 + 사유

- 다중 선택 추가(여러 책 한 번에), 라이브러리 검색 인라인.
- **`reason`을 사용자에게 개방**: 연결 시 선택적으로 "왜?" 한 줄(예: 같은 작가, 주제 연속, 반박 관점). admin 전용 마이그레이션 주석을 사용자 허용으로 변경.
- (확장) 노트 에디터에서 `@책제목` 멘션 → 자동 연결 + 사유=노트 제목. 이미 `syncBookRelationsFromNote` 기반 존재.

### F5. 자동 연결 제안 (Discovery)

- 규칙 기반 후보: 같은 저자 / 같은 서가 / 같은 기간 독서 / 노트에서 함께 언급. "추천 연결" 카드로 노출 → 원클릭 수락.
- (장기) 임베딩 기반 유사 책 추천. 현재 AI 인프라(`app/actions/ai/*`) 재사용 여지.

### F6. 고립·약연결 발견

- 전역 그래프에서 "연결 0개 책" 필터 → 묻혀 있던 책을 다시 잇도록 유도. 독서 회고 가치.

## 6. 데이터 모델 변경

대부분 **기존 스키마로 충분**하다. 추가 제안:

1. **`reason` 사용자 개방** — 스키마 변경 없음. 서버 액션(`addBookRelation`)에 `reason?` 파라미터 추가, RLS 그대로. UI에서 입력.
2. **연결 출처 구분(선택)** — `origin` 컬럼(`'manual' | 'note' | 'suggestion'`) 추가 시 F3의 출처 배지·분석이 정확해짐. NULL 기본 `'manual'`로 idempotent 마이그레이션.
3. **양방향 저장 유지 여부 재검토(선택·장기)** — 현재 2행 저장은 그래프 조회 시 중복 제거 로직(admin의 `dedupeKey`)을 강제. 단방향 1행 + 조회 시 OR로 바꾸면 저장 절반이지만 마이그레이션 리스크 큼 → **이번 범위에서는 현행 유지** 권장.

> 마이그레이션 규칙 준수: `doc/database/migration-YYYYMMDDHHmm__user_book_relations__<내용>.sql`, idempotent, 테이블 생성 아님(컬럼 추가)이므로 RLS는 기존 정책 승계.

## 7. 아키텍처 / 재사용 전략

핵심은 **admin 그래프 엔진의 공용화**다.

```
components/admin/book-relations-graph.tsx      (admin 전용, 전 사용자 데이터)
        │  ── 물리/렌더 로직 추출 ──▶
components/graph/knowledge-graph.tsx           (공용: nodes/edges props만 받음)
        ├─▶ app/(main)/library/graph           (F1 사용자 전역 지도)
        ├─▶ components/books/local-graph.tsx    (F2 책 상세 로컬)
        └─▶ components/admin/...                (기존 admin 재사용)
```

- 레이어 규칙 준수: 데이터는 `app/actions/book-relations.ts`에 **사용자용 그래프 데이터 액션** 신설(`getUserGraph()`: 노드=내 책, 엣지=내 연결, connectionCount 집계). admin의 `GraphNode/GraphEdge` 타입을 공용 타입으로 승격.
- `components/ → hooks/ → app/actions/ → Supabase` 분리 유지. 그래프 컴포넌트는 순수 표현, 데이터 fetch는 서버.
- 모바일: SVG 그래프는 터치 팬/핀치줌 필요. 좁은 화면에서는 로컬 그래프를 리스트로 폴백하는 반응형 분기.

## 8. 단계별 로드맵

| 단계 | 범위 | 산출물 | 난이도 |
|------|------|--------|--------|
| **P0 — 엔진 추출** | admin 그래프 → 공용 `<KnowledgeGraph>`, 공용 타입, `getUserGraph()` 액션 | 재사용 기반, 기능 변화 없음(리팩터) | 중 |
| **P1 — 전역 지도(F1)** | `/library/graph` + 인스펙터 + 빈 상태 온보딩 | 사용자 첫 "한눈에 보기" | 중 |
| **P2 — 로컬 그래프 + 사유(F2,F4)** | 책 상세 미니 그래프, 다중 추가, `reason` 개방 | 탐색·생성 경험 | 중 |
| **P3 — 맥락 패널(F3)** | 책↔책/책↔노트 통합, 출처 배지(+`origin` 컬럼) | 백링크 경험 완성 | 중상 |
| **P4 — 제안·고립 발견(F5,F6)** | 규칙 기반 추천, 고립 필터 | 능동적 연결 유도 | 상 |

권장 착수: **P0 → P1**을 1차 마일스톤으로. 사용자 가치(전역 조망)가 가장 크고, 기존 자산 재사용으로 비용 대비 효과가 높다.

## 9. 리스크 및 고려사항

- **성능**: 다독 사용자(수백 권·수천 연결)에서 O(n²) 반발 계산 부하. → 노드 상한·바넷헛 근사 또는 정적 레이아웃 캐시. 우선은 상한+디그레이드.
- **빈 상태**: 연결이 거의 없는 사용자에게 그래프는 공허. F4·F5의 온보딩/제안이 동반되어야 채택됨.
- **양방향 2행 중복**: 사용자 그래프 액션에서도 admin과 동일한 dedupe 필요(공용 헬퍼화).
- **모바일 UX**: 그래프 인터랙션이 모바일에서 까다로움 → 리스트 폴백 필수.
- **자동 파생 연결의 노이즈**: 노트 기반 자동 연결이 그래프를 과밀하게 만들 수 있음 → 출처 필터로 "직접 연결만 보기" 제공.

## 10. 미결 의사결정 (검토 요청)

1. **1차 범위**: P0+P1(전역 지도)만 먼저 vs. P2(로컬 그래프)까지 묶어서?
2. **진입점**: 전역 지도를 별도 라우트 vs. 서재 화면 내 뷰 토글?
3. **로컬 그래프**: 기존 썸네일 리스트를 **교체** vs. 리스트/그래프 **토글 공존**?
4. **`origin` 컬럼**: 출처 구분을 위해 이번에 도입할지(P3 선반영) vs. 보류?
5. **자동 제안(F5)**: 규칙 기반으로 충분 vs. AI 임베딩까지 목표?

위 5개에 대한 방향만 정해주시면 선택된 범위로 상세 설계(데이터 액션 시그니처, 컴포넌트 props, 마이그레이션 초안)로 진행하겠습니다.
