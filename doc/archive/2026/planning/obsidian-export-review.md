# 옵시디언 내보내기(Export to Obsidian Vault) 검토

> 작성일: 2026-06-15 · 상태: 검토(Review) · 관련: [book-relations-obsidian-improvement.md](./book-relations-obsidian-improvement.md)
> 아이디어: 현재 서재·연결 데이터를 **옵시디언 볼트(Markdown + `[[위키링크]]`) ZIP으로 내보내 다운로드** → 사용자가 옵시디언에서 그래프로 바로 사용

---

## 0. 결론 (TL;DR)

**기술적 실현성: 매우 높음 / 구현 비용: 낮음.** 앱 내 그래프 엔진을 만들 필요 없이, 옵시디언이 제공하는 그래프·로컬그래프·백링크·검색·플러그인을 **공짜로** 얻는다. 데이터 모델도 이미 내보내기에 충분하다(추가 스키마 변경 불필요).

**다만 한 가지 분명히 할 것:** 이 기능은 **첫 기획의 "앱 안에서 한눈에 보기"와 다른 사용자층**을 위한 것이다. 내보내기는 옵시디언을 이미 쓰는 **파워 유저·데이터 소유 지향 사용자**에게 가치가 크고, 일반 사용자(앱에서 바로 보고 싶은)에게는 도움이 적다. 둘은 경쟁 관계가 아니라 **상호 보완**이며, 내보내기는 **빠르게 출시 가능한 별개의 퀵윈**으로 다루길 권한다.

---

## 1. 왜 좋은 방향인가

- **유지보수 자산이 거의 없음**: force 시뮬레이션·줌·드래그·성능 튜닝을 직접 떠안지 않아도 된다. 옵시디언이 다 한다.
- **풍부한 결과물**: 그래프뿐 아니라 로컬 그래프, 백링크 패널, 전문 검색, 태그, 사용자 플러그인까지 사용자가 활용.
- **데이터 소유권·신뢰**: "내 독서 데이터를 표준 Markdown으로 가져갈 수 있다"는 락인 없는 메시지. 파워 유저 호감도 높음.
- **현재 데이터로 충분**: `books`, `user_books`, `user_book_relations`, `notes` 매핑만으로 완결.

---

## 2. 데이터 → 볼트 매핑

| 원본 | 옵시디언 표현 |
|------|---------------|
| `user_books` 1건 | 책 노트 1개 (`<책제목>.md`) |
| `books.title/author/publisher/category/...` | YAML frontmatter |
| `user_books.status/started_at/completed_at/reading_reason/book_format` | frontmatter (독서 상태·기간) |
| `user_book_relations` (+`reason`) | 본문 `## 연결된 책` 아래 `[[대상책]] — 사유` 위키링크 → **그래프 엣지** |
| `notes` (기록) | 책 노트 본문에 섹션으로 임베드 **또는** 노트별 `.md`로 분리(노드 추가) |
| `notes.related_user_book_ids` | 해당 노트에서 `[[책]]` 위키링크 |
| `notes.tags` / 서가(`bookshelves`) | `#태그` / 폴더 분류 |
| `books.cover_image_url` | 원격 URL 임베드 **또는** `attachments/`에 다운로드 |

### 책 노트 예시 (`자기 신뢰.md`)

```markdown
---
title: 자기 신뢰
author: 랄프 왈도 에머슨
publisher: 현대지성
category: 인문
isbn: 9791234567890
status: 완독
started: 2026-03-01
finished: 2026-03-20
format: 종이책
tags: [인문, 고전]
aliases: [Self-Reliance]
cover: https://.../cover.jpg
---

![cover](https://.../cover.jpg)

> 읽은 이유: 자아와 독립적 사고에 대한 고전을 찾다가.

## 연결된 책
- [[데미안]] — 자아 형성이라는 같은 주제
- [[월든]] — 같은 초월주의 계열

## 기록
### 인용 (p.42)
스스로를 믿어라. 모든 마음은 그 강철 같은 줄에 진동한다.

### 메모 (p.88)
순응에 대한 비판이 현대 SNS 시대에도 유효하다.
```

→ 옵시디언에서 이 파일들을 열면 `[[ ]]`가 자동으로 그래프 엣지가 되고, `데미안.md`에는 백링크가 자동 생성된다.

## 3. 핵심 설계 결정 (내보내기 포맷)

1. **위키링크 해석 = 파일명/별칭 매핑**
   - `user_book_id → 책제목` 맵을 만들고, 제목으로 `[[ ]]` 생성.
   - **제목 충돌·금지문자**(`/ \ : * ? " < > |`) 처리 필수: 파일명은 새니타이즈하고, 원제목은 `aliases`에 보존해 링크 깨짐 방지.
2. **양방향 2행 → 1엣지 dedupe**: `user_book_relations`는 A→B, B→A 두 행. 한쪽 노트에만 링크를 써도 옵시디언이 백링크를 만들지만, 그래프 일관성을 위해 **정렬된 쌍 기준으로 dedupe 후 양쪽 모두에 기재** 권장(admin의 `dedupeKey` 로직 재사용).
3. **기록(notes) 단위**: ① 책 노트에 임베드(간결) vs. ② 노트별 파일(그래프 노드가 풍부, 진짜 옵시디언스러움). → **옵션 토글** 제안, 기본은 임베드.
4. **표지 이미지**: 원격 URL(가벼움·오프라인 불가) vs. `attachments/` 동봉(용량↑·오프라인 OK). → 기본 원격 URL, "이미지 포함" 옵션.
5. **폴더 구조**: 평면 vs. 서가(`bookshelves`)별 폴더 vs. 상태별. → 서가별 폴더 권장(사용자 멘탈모델 일치).
6. **동봉물**: `README.md`(사용법), 선택적 `.obsidian/graph.json`(그래프 색상·필터 프리셋) 동봉 시 첫 경험 향상.

## 4. 구현 스케치

- **서버 액션 또는 API 라우트**: `app/api/export/obsidian/route.ts` (스트리밍 ZIP) 또는 `app/actions/export/obsidian-vault.ts`.
  - RLS로 본인 데이터만 조회(`getCurrentUser()` → 본인 `user_books`/`relations`/`notes`).
  - 메모리에서 파일 트리 구성 → `jszip`(또는 `archiver`)로 ZIP → `Content-Disposition: attachment`.
- **레이어 규칙 준수**: 데이터 조회는 `app/actions/`(또는 라우트 핸들러 내 서버 클라이언트), 파일/ZIP 생성은 유틸(`lib/export/obsidian.ts`)로 분리.
- **진입점**: 설정 또는 서재 화면에 "옵시디언으로 내보내기" 버튼 + 옵션 모달(기록 분리 여부, 이미지 포함 여부).
- **규모 고려**: 수천 권 사용자는 ZIP 생성 시간/메모리 주의 → 스트리밍 또는 백그라운드 생성 후 다운로드 링크.

> 신규 의존성(`jszip` 등) 추가 시 번들/서버 라이선스 확인. 마이그레이션·DB 변경은 **불필요**.

## 5. 장단점 / 리스크

**장점**: 낮은 구현비, 유지보수 부담 거의 없음, 옵시디언 기능 전체 무료 획득, 데이터 소유권 메시지, 빠른 출시.

**한계·리스크**:
- **정적 스냅샷**: 내보낸 시점 고정. 데이터가 바뀌면 재내보내기 필요(주기적 재export 안내로 완화).
- **대상층 협소**: 옵시디언 사용/학습이 전제. 일반 사용자에게는 효용 낮음 → **첫 기획의 인앱 그래프를 대체하지 못함**.
- **단방향 이동**: 옵시디언에서 한 편집은 앱으로 돌아오지 않음(역동기화는 별도 대형 과제, 범위 밖).
- **모바일 사용자**: 옵시디언 볼트 활용이 번거로움.
- **링크 무결성**: 제목 충돌/특수문자/중복 제목 처리 미흡 시 그래프가 깨짐 → 새니타이즈·별칭 전략이 품질의 핵심.
- **이미지·개인정보**: 원격 URL 만료 가능성, 공개/비공개 기록 구분(본인 데이터만이라 RLS로 안전하나 export 옵션에서 명시).

## 6. 인앱 그래프(첫 기획) 대비 — 무엇을 먼저?

| 기준 | 옵시디언 내보내기 | 인앱 그래프(이전 기획) |
|------|------------------|------------------------|
| 대상 | 파워 유저·데이터 소유 지향 | 일반 사용자(다수) |
| 구현비 | 낮음 | 중(엔진은 이미 보유, 추출·연결 필요) |
| 유지보수 | 거의 없음 | 지속(성능·UX) |
| "한눈에 보기" 충족 | 앱 밖에서만 | 앱 안에서 즉시 |
| 출시 속도 | 빠름 | 중 |

**권장 순서**: 내보내기는 **독립 퀵윈으로 먼저 출시**해 데이터 소유권 가치를 빠르게 제공하고, 일반 사용자용 "한눈에 보기"는 별도 트랙으로 인앱 로컬 그래프(F2)부터 점진 도입. 둘은 충돌하지 않는다.

## 7. 미결 의사결정 (검토 요청)

1. **기록(notes) 처리**: 책 노트에 임베드(기본) vs. 노트별 파일 분리 — 기본값과 옵션 노출 범위?
2. **표지 이미지**: 원격 URL(기본) vs. ZIP 동봉 옵션 제공 여부?
3. **폴더 구조**: 서가별 vs. 평면 vs. 상태별?
4. **진입점/규모**: 동기 다운로드로 충분 vs. 대용량 대비 비동기 생성?
5. **포지셔닝**: 내보내기를 인앱 그래프 대신 **이번 우선 과제로 단독 진행**할지, 아니면 인앱 그래프와 병행할지?

위 방향을 정해주시면 포맷 스펙 확정 + 내보내기 유틸/라우트 구현 설계로 바로 진행하겠습니다.
