2. Agent Architecture

에이전트는 기능 단위가 아닌 판단 책임의 경계를 기준으로 분리합니다. 각 에이전트는 명확한 입출력 스키마를 가지며, 자신의 판단 범위를 초과하면 오케스트레이터로 에스컬레이션합니다.

  Agent Orchestration Architecture
  =================================

                        ┌─────────────────────┐
                        │   Orchestrator       │
                        │   (의사결정·종합)     │
                        └──────┬──────────────┘
                               │
            ┌──────────────────┼──────────────────────┐
            │                  │                      │
    ┌───────▼──────┐  ┌───────▼──────┐  ┌───────────▼────────┐
    │  Core Domain │  │   Platform   │  │   Operations       │
    │  Agents      │  │   Agents     │  │   Agents           │
    ├──────────────┤  ├──────────────┤  ├────────────────────┤
    │ Library      │  │ AI           │  │ Performance        │
    │ Records      │  │ Search       │  │ Data (DB/Migration)│
    │ Groups       │  │ Admin        │  │ Deploy             │
    │ Auth/Identity│  │ FreeNotes    │  │ Test               │
    └──────────────┘  └──────────────┘  └────────────────────┘

  Design Principles:
  ─────────────────
  1. 에이전트는 "재료"를 제공, 오케스트레이터가 "결정"
  2. 불확실성 라벨링 필수 (info_insufficient / conflicting / out_of_scope)
  3. 구조화 출력(JSON/MD) = 다른 에이전트 입력용
  4. 자연어 출력 = 최종 사용자 전달용

3. Orchestrator Agent

모든 에이전트를 조율하는 최상위 의사결정자. 직접 코드를 작성하지 않으며, 각 도메인 에이전트에게 작업을 위임하고 결과를 종합합니다.

O

Orchestrator

orchestrator.md
CORE NEW

유저 요청을 분석하여 적절한 도메인 에이전트에게 라우팅. 복수 에이전트의 결과를 종합하여 최종 의사결정을 수행합니다.

Responsibilities

  • 유저 요청 의도 파악 및 도메인 분류
  • 적절한 에이전트에게 작업 위임 (병렬/순차)
  • 에이전트 간 의존성 관리 및 순서 조율
  • 에스컬레이션된 불확실성에 대한 최종 판단
  • Task Summary 생성 및 변경 파일 목록 취합

Routing Rules

  Request Pattern                  → Agent
  ──────────────────────────────────────────
  "책 추가/삭제/상태 변경"         → Library Agent
  "기록 작성/수정/OCR"             → Records Agent
  "자유기록 관련"                   → FreeNotes Agent
  "AI 채팅/리포트/페르소나"        → AI Agent
  "모임 생성/멤버/공유"            → Groups Agent
  "로그인/회원가입/온보딩"         → Auth Agent
  "검색 기능"                       → Search Agent
  "관리자 기능"                     → Admin Agent
  "성능 최적화"                     → Performance Agent
  "DB 스키마/마이그레이션"         → Data Agent
  "배포/환경 설정"                  → Deploy Agent
  "테스트 작성/실행"                → Test Agent
  "복수 도메인 걸침"               → 병렬 위임 후 종합

Escalation Handling

Orchestrator가 직접 판단하는 경우
  • 아키텍처 변경이 필요한 요청 (레이어 간 의존성 변경)
  • 복수 에이전트의 결과가 상충할 때
  • 보안 관련 의사결정 (RLS 정책, 인증 로직)
  • 유저에게 되물어야 하는 애매한 요청

P

Performance Agent

performance-agent.md
OPS EXTENDS mobile_performance_rule.md

기존 mobile_performance_rule.md를 확장합니다. LCP/FID/CLS 기준 준수, React.memo/useCallback 최적화, 이미지 최적화, 번들 분석 등을 담당합니다.

  • 이미지 최적화 (WebP 변환, lazy loading)
  • 모바일 터치 타겟 크기 검증 (최소 44x44px)
  • Suspense/streaming SSR 최적화
  • transition-all 사용 금지 검증

Quality Criteria

17. Orchestration Flow Example

실제 유저 요청이 처리되는 흐름 예시

Example: "책에 새 기록을 추가하고, AI 태그 자동 생성해줘"

1

Orchestrator: 요청 분석

도메인 분류 → Records (기록 생성) + AI (자동 태깅). 두 에이전트 순차 호출 필요.

2

Records Agent: 기록 생성

useNoteForm 훅 → createNote action → notes 테이블 INSERT → 포인트 적립 (earnPoints). 생성된 note_id 반환.

3

AI Agent: 자동 태깅

note_id의 content를 입력으로 → /api/ai/auto-tag 호출 → Gemini 2.0 Flash → 태그 3-5개 생성 → notes.tags 업데이트.

4

Orchestrator: 결과 종합

Records Agent 결과 (note 생성 성공) + AI Agent 결과 (태그 5개 생성) → 유저에게 최종 응답 생성.

Example: "모임에 새 테이블 추가하고 관련 UI 만들어줘"

1

Orchestrator: 요청 분석

도메인 분류 → Data (스키마 변경) + Groups (UI). Data Agent 먼저, Groups Agent 이후 (의존성).

2

Data Agent: 스키마 설계

DATA_MODEL.md 업데이트 → migration SQL 작성 (idempotent) → RLS 4개 정책 → types/database.ts 동기화.

3

Groups Agent: UI 구현

Data Agent의 스키마를 기반으로 → Server Action 작성 → 컴포넌트 구현 → 훅 연동.

4

Orchestrator: 결과 종합 + Task Summary

변경 파일 목록 취합 → Task Summary 생성 → 유저에게 전달.
