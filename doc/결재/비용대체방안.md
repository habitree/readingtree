> **현재 비용**: 월 ₩7~8천 (대부분 Cloud Vision API)
> **목표**: ₩0 ~ ₩2,000 / 월 또는 사용자 증가에도 비례 폭증하지 않는 구조
> **현재 코드 진입점**: `lib/api/cloud-run-ocr.ts`의 `extractTextFromImage(imageUrl)`

## 옵션 A. 현행 유지 — 현실 비용 한도 추정

**그대로 두면**:
- 사용자 100명, 월 평균 20회 OCR → 2,000회 / 월 → 무료 티어 1,000 차감 → 1,000회 과금 → 약 ₩2,000
- 사용자 1,000명 → 20,000회 → ~₩40,000 / 월
- 사용자 10,000명 → ~₩400,000 / 월

**즉, 사용자 수에 선형 비례.** 현재(7,558원)는 활성 사용자 수가 적어서 부담이 적지만, 성장 시 가장 먼저 터질 비용 항목.

## 옵션 B. Gemini Vision으로 통합 ★★★ (강력 추천)

### 왜 1순위인가
1. **Gemini API 키와 클라이언트(`@google/generative-ai`)가 이미 코드에 있음**.
2. Gemini 2.0 Flash는 멀티모달이라 이미지에서 텍스트 추출이 가능하고, 한국어 OCR 정확도가 실용 수준.
3. **AI Studio 무료 티어가 큼**: Gemini 2.0 Flash 무료 1,500 요청/일 (월 ~45,000건).
4. Cloud Run + Vision API 조합을 **둘 다 폐기**할 수 있어 비용 0원에 근접.
5. OCR 후 어차피 "이 텍스트가 책 제목인지 판단" 단계가 Gemini로 또 가는데, **OCR과 분류를 한 번의 호출로** 합칠 수 있음 → 호출 수 자체가 줄어듦.

### 단점
- AI Studio API의 quota 정책이 바뀔 수 있음 (정책 변경 리스크).
- 응답 시간이 Vision API보다 약간 길 수 있음 (~수백 ms~수초).
- 결정성(determinism)이 Vision API보다 낮음 → 같은 이미지에 결과가 미세하게 다를 수 있음.

### 작업 스케치

```ts
// lib/api/gemini-ocr.ts (신규)
import { GoogleGenerativeAI } from "@google/generative-ai";

const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);

export async function extractTextFromImageGemini(imageUrl: string) {
  const res = await fetch(imageUrl);
  const buf = await res.arrayBuffer();
  const base64 = Buffer.from(buf).toString("base64");
  const mimeType = res.headers.get("content-type") || "image/jpeg";

  const model = genAI.getGenerativeModel({ model: "gemini-2.0-flash" });
  const result = await model.generateContent([
    { inlineData: { data: base64, mimeType } },
    { text: "이 이미지에서 보이는 모든 한글/영문 텍스트를 줄바꿈을 유지해 그대로 추출해줘. 설명 없이 텍스트만." },
  ]);
  return result.response.text().trim();
}
```

이후 `lib/api/cloud-run-ocr.ts` 호출처를 위 함수로 치환 → 트래픽 일부(예: 10%)만 Gemini로 보내며 정확도 비교 → OK이면 100% 전환 → Cloud Run 함수와 Vision API 사용 중단.

### 예상 비용
- 무료 티어 안에 머물 가능성 매우 높음 → **₩0 / 월**.
- 무료 티어 초과 시: gemini-2.0-flash 입력 $0.075/1M tok, 출력 $0.30/1M tok → 월 수만 호출에도 ₩수백~수천 수준.

## 옵션 C. Tesseract.js (클라이언트 OCR)

### 장점
- **완전 무료, 외부 API 호출 0**.
- 사용자 브라우저에서 처리 → 서버 비용 ₩0, 개인정보가 서버에 안 감.

### 단점
- **한글 정확도가 낮음**. 책 표지처럼 디자인 폰트가 들어가면 오차 큼.
- 첫 사용 시 트레이닝 데이터(~10MB) 다운로드 필요.
- 모바일 저사양 기기에서 느림.

### 사용 시나리오
- "OCR 실패 시 fallback" 또는 "프리뷰 단계의 빠른 추출"용 보조.
- Gemini로 전환하되, 네트워크 실패 시 클라이언트에서 1차 시도하는 구조.

---

## 옵션 D. Naver Clova OCR (한글 특화 대안)

### 장점
- **한글 정확도 업계 최상위**. 책 표지·필사 인식에 강점.
- 무료 티어 1,000장/월 (General OCR API).
- 국내 서비스 → 결제 KRW, 부가세 처리 단순.

### 단점
- 콘솔에서 도메인 등록·시크릿 발급 필요 (추가 작업).
- 무료 초과 시 General OCR ₩4/장, Document OCR은 더 비쌈.
- Vision API와 가격 차이 크지 않음 — 비용 절감보다 **정확도**가 동기.

### 추천 시점
- 한글 책이 압도적이고 사용자가 OCR 결과 부정확 불만을 제기할 때.

---

## 옵션 E. OpenAI gpt-4o-mini Vision

### 장점
- 정확도 우수, 한국어도 자연스럽게.

### 단점
- **무료 티어 없음**.
- OpenAI 계정 별도 관리 필요 → 결제 분산.

### 추천도
- 이미 OpenAI를 핵심 LLM으로 쓰는 경우에만 합리적. 현재는 Gemini 중심이라 굳이 추가할 필요 없음.

---

## 옵션 F. 현행 유지 + 즉시 적용 가능한 비용 절감 패치

대체 안 하더라도 **이번 주 안에** 할 수 있는 비용 억제:

### F-1. 이미지 hash 기반 캐시
- 같은 이미지 URL이면 결과 재사용.
- Supabase에 `ocr_cache (image_hash text PK, text text, created_at)` 테이블 → RLS 적용.
- 동일 책 여러 번 등록되는 케이스 잡으면 호출 수 30~50% 감소 가능.

### F-2. 사용자별 호출 제한 (Rate Limit)
- 메모리에 따르면 Supabase `rate_limits` 테이블 + RPC로 이미 한도 인프라 있음. OCR도 사용자당 일 5~10회로 제한.
- 봇/abuse 방어 효과도 있음.

### F-3. 클라이언트에서 사전 압축
- 책 사진을 클라이언트에서 1024px·85% JPEG으로 다운샘플 → 업로드 크기·처리 속도 개선 (Vision API 단가는 사이즈와 무관하지만 속도/네트워크 절감).

### F-4. Cloud Run 인증 강화
- 현재 함수가 unauthenticated면 외부 abuse 가능 → 서비스 계정만 호출 가능하도록 `roles/run.invoker` 제한.
- IAM 한 줄로 끝나는 작업이지만 의외로 큰 비용 누수 차단.

### F-5. 예산 알림 (반드시!)
- 월 ₩10,000 도달 시 이메일 → 100% 도달 시 Pub/Sub로 자동 비활성화 옵션.

```
즉시 (이번 주):
  1. F-5 예산 알림 설정 (3분)

  3. F-1 OCR 결과 캐싱 (반나절)
  4. F-2 사용자별 일 호출 제한 (반나절)

  5. 옵션 B - Gemini Vision PoC (반나절)

  7. OK이면 100% 전환 → Cloud Run·Vision 사용 중단 (1일)

중장기 (필요 시):
  8. 한글 정확도 이슈가 생기면 옵션 D Clova OCR 추가
  9. 사용자 1만 명+ 도달 시 다시 비용 모델 재검토
```
