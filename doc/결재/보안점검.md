## 🔥 데이터로 입증된 1순위 가설 (2026-05-04 백필 후)

월별 OCR 실제 호출 카운트 vs GCP 청구의 비교가 **자동 호출이 원인**임을 증명했습니다.

| 월 | 실제 사용자 OCR (`ocr_logs`) | GCP 청구 (Vision API 추정) | 차이 (= 자동 호출) |
|---|---|---|---|
| 2025-12 | 2건 | (해당 없음) | - |
| 2026-01 | 308건 | (해당 없음) | - |
| 2026-02 | 13건 | (확인 필요) | - |
| 2026-03 | 6건 | ~₩7,558 청구 | 약 **5,000건 추정** |
| **2026-04** | **2건** | **₩7,462 청구 (~5,000회)** | **약 4,998건** |

→ 4월에 사용자가 만든 transcription 노트는 **단 2건**인데 GCP에 약 **5,000회** 청구가 들어왔습니다. 차이 4,998회가 정확히 `testOcrConnection` 자동 호출 패턴(admin이 `/admin/api-info` 페이지를 진입할 때마다 1회 호출)과 일치합니다.

→ 1순위 패치(`testOcrConnection` 토큰 검증까지만)가 적용된 5월부터는 **사용자 OCR 카운트 ≈ GCP 청구**가 되어야 합니다. 5월 결제일에 변화를 추적하면 가설이 최종 확정됩니다.

## 🚨 추가 발견 (2026-05-04) — admin OCR 사용량 페이지 부정확 원인

### 증거 (백필 전 상태)

```
ocr_logs.success      :   8건
transcriptions.completed: 318건
→ 누락 310건 (admin 페이지에서 보이지 않던 데이터)
```

### 원인

`ocr_logs` / `ocr_usage_stats` 테이블에 **SELECT(admin) 정책만 있고 INSERT/UPDATE 정책이 없음**. 그러나 `recordOcrSuccess` / `recordOcrFailure`는 `createServerSupabaseClient` (사용자 세션 클라이언트)로 동작 → RLS에 의해 INSERT가 차단됨.

`ocr_logs` 데이터가 2026-01-15~16에만 19건이 기록되고 그 이후로 멈춘 이유. 추정: 1/16 직후에 RLS가 강화되면서 INSERT가 막혔는데 코드는 그대로 유지됨.

### 적용된 패치

1. **백필 (`migration-202605041000`)**:
   - 312건 누락된 OCR을 `transcriptions` 기반으로 `ocr_logs`에 채움
   - `ocr_usage_stats`를 사용자별 합계로 재계산 (upsert)
   - INSERT/UPDATE/SELECT RLS 정책 추가 (본인 user_id에 한해 허용)
2. **코드 수정 (`app/actions/ai/ocr.ts`)**:
   - `recordOcrSuccess` / `recordOcrFailure`가 `createAdminSupabaseClient` (service_role)를 사용하도록 변경
   - 앞으로는 RLS와 무관하게 통계가 항상 기록됨

### 백필 결과 (적용 후)

```
ocr_logs                  : 19 → 331 (+312)
ocr_logs.success          :  8 → 319
ocr_logs.failed           : 11 →  12
ocr_usage_stats users     :  ? →   2 (success=318, failure=1)
```

→ 이제 `/admin/api-info` 페이지의 OCR 사용량 카드가 정확한 카운트를 표시합니다.

## 🟡 3순위 — 결과 캐시 부재로 동일 이미지 중복 호출

### 증거

`lib/api/cloud-run-ocr.ts` 전체 — 캐시 레이어 없음.

발생 시나리오:
- 사용자가 같은 책 사진을 여러 번 업로드 (다른 노트 ID로)
- 사용자가 노트를 삭제했다가 다시 같은 사진으로 업로드
- 사용자가 retry 버튼을 여러 번 누름 (현재 가드는 `isRetrying` boolean 한 번만 막음 — 새로고침하면 다시 가능)
- admin batch가 같은 노트를 다시 처리 (위 2순위와 결합)

### 패치 (이미지 콘텐츠 hash 기반)

```ts
// lib/api/cloud-run-ocr.ts에 캐시 추가
import crypto from "crypto";

const buffer = await imageResponse.arrayBuffer();
const hash = crypto.createHash("sha256").update(Buffer.from(buffer)).digest("hex");

// Supabase에서 캐시 확인
const { data: cached } = await supabase
  .from("ocr_cache")
  .select("text")
  .eq("image_hash", hash)
  .maybeSingle();
if (cached) {
  console.log("[Cloud Run OCR] 캐시 hit");
  return cached.text;
}
// 호출 후 결과 캐싱
await supabase.from("ocr_cache").insert({ image_hash: hash, text: extractedText });
```

테이블:
```sql
create table ocr_cache (
  image_hash text primary key,
  text text not null,
  created_at timestamptz default now()
);
alter table ocr_cache enable row level security;
create policy "service_role only" on ocr_cache for all using (false); -- API 라우트(서비스키)에서만 접근
```

같은 이미지에 대한 호출은 1번으로 줄어듦 → **재시도 비용 0원**.

## 추가로 확인해야 할 잠재 위험

### A. GPT/AI 보정의 별도 비용

`app/api/ocr/process/route.ts:78-93`이 OCR 후 자동으로 `correctOcrText()` 호출.
- GCP 비용은 아니지만 **OpenAI/Gemini 별도 청구**.
- OCR 호출 1건 = 보정 호출 1건.
- 위 1·2순위 자동 호출이 발생하면 **OpenAI/Gemini 비용도 같이 폭증**.

→ `testOcrConnection`은 보정을 안 거치지만, `batchProcessOCR`도 내부에서 보정 안 함(직접 `extractTextFromImage`만 호출). 다행. 사용자 정상 경로에서만 보정 비용 발생.

### B. 중복 호출 (race condition)

`/api/ocr` POST 후 `after()`로 `/api/ocr/process`를 fetch하는 구조에서:
- 사용자가 클라이언트에서 같은 요청을 빠르게 두 번 보내면(네트워크 더블 클릭) → after()가 두 번 실행 → Vision API 두 번.
- 현재 가드: rate limit 분당 15회뿐. 같은 noteId 중복은 못 막음.

→ `transcription` 테이블에 `processing` 상태 row가 이미 있으면 새 요청 거부:
```ts
const { data: existing } = await supabase
  .from("transcriptions")
  .select("status").eq("note_id", noteId).maybeSingle();
if (existing && existing.status === "processing") {
  return NextResponse.json({ error: "이미 처리 중입니다." }, { status: 409 });
}
```

### C. 이미지 URL 검증 우회

`/api/ocr` route는 `imageUrl`을 클라이언트가 보낸 그대로 받음. 외부 URL을 넣어도 통과.
- abuse: 엄청 큰 외부 이미지 URL을 자기 noteId에 매핑해서 OCR 호출 → 비용 발생.
- 가드: noteId 소유권 + 그 노트의 image_url과 요청 imageUrl이 일치하는지 검증해야 함.

`/api/ocr/process/route.ts:61` `verifyNoteOwnership`은 noteId 소유만 확인하지 imageUrl이 그 노트의 것인지는 확인하지 않음.

→ 패치:
```ts
const note = await getNoteById(noteId, user.id);
if (note.image_url !== imageUrl) {
  return NextResponse.json({ error: "이미지 URL이 노트와 일치하지 않습니다." }, { status: 400 });
}
```

## 결론

> **핵심**: 비용은 OCR을 많이 써서가 아니라, **admin 대시보드가 페이지 진입 시마다 진짜 Vision API를 호출하기 때문**일 가능성이 가장 높음.

위 1순위 패치 한 줄만 제거해도 비용이 거의 0에 수렴할 가능성이 매우 높음. 그 후 `비용대체방안.md`의 옵션 B(Gemini Vision)로 단계적 전환하면 사용자 증가에도 비용이 폭증하지 않는 구조로 갈 수 있음.

검증 순서:
1. **이번 주 안**: 1순위 패치 → 다음 결제일까지 비용 변화 관측
2. **다음 결제일 (5/1 ~ 5/30)**: 변화 없으면 2~4순위로 범위 확대
3. **6월부터**: Gemini Vision 전환 PoC
